# 먼저가요, 창원

창원 지역 돌봄 담당자가 누구를 먼저 확인하고, 어떤 복지혜택을 안내하며, 이후 조치를 어떻게 이어갈지 관리하는 웹 서비스입니다.

사회복지사, 생활지원사, 방문건강간호사 등 실무자가 담당 대상자의 우선순위를 확인하고 방문과 전화 계획, 현장 기록, 혜택 신청지원, 기관 연계, 주간 보고를 하나의 흐름으로 처리합니다. 어르신이 직접 앱을 설치하거나 조작하는 것을 전제로 하지 않습니다.

현재는 빈 역할별 폴더와 루트 파일을 준비한 초기 단계입니다. main.py·Dockerfile·compose.yaml은 빈 파일이며, 서버·DB 연결·API 실행은 이후에 구현합니다. 패키지는 설치하지 않았습니다.

## 초기 파일 상태

| 항목 | 현재 상태 |
| --- | --- |
| config, dto, handler, service, util, data, tests | 내부 파일 없이 빈 폴더로 생성 |
| main.py, Dockerfile, compose.yaml | 빈 파일로 생성 |
| .gitignore, .dockerignore | 환경변수·캐시·개발 파일 제외 규칙 작성 |
| .env.example | DB 접속 정보·Origin·세션·외부 API 키 설정 예시 |
| requirements.txt | FastAPI·Uvicorn 기본 패키지 목록 작성 |
| [Swagger 문서](swagger.yaml) | 인증 API 세 개의 OpenAPI 초안 |

swagger.yaml은 [Swagger Editor](https://editor.swagger.io/)에서 열어 확인할 수 있습니다. 로그인 POST /auth/login, 내 정보 GET /auth/me, 로그아웃 POST /auth/logout을 문서화했습니다. 서버 주소·쿠키 이름·응답 형식은 초기 제안이며 구현하면서 맞춥니다. 세션 만료시간은 아직 정하지 않았습니다.

## 업무 흐름

1. 대상자 파악: 배정된 대상자의 건강, 가구형태, 수급 정보와 이전 확인 이력을 조회합니다.
2. 우선순위 검토: 점수와 추천 근거를 확인하고 방문, 전화, 모니터링 큐를 검토합니다.
3. 계획 확정: 담당자가 연락 방식과 예정일시를 정하고 필요하면 사유를 남겨 보류하거나 변경합니다.
4. 현장 기록: 체크리스트, 연락 결과, 위기 여부, 다음 확인일을 저장합니다.
5. 지원과 연계: 혜택 후보를 확인하고 신청지원 과정 및 기관 연계 진행 상태를 기록합니다.
6. 주간 보고: 확인 실적, 혜택 지원, 연계 진행 상황과 미조치 사유를 집계합니다.

최종 방문 여부, 신청지원과 기관 연계는 담당자가 판단합니다. 시스템은 우선순위와 근거를 제공하며 추천 계획을 자동 확정하지 않습니다.

## 구현 범위

P0는 업무 흐름에 필요한 필수 기능, P1은 지역 현황과 지도 및 일부 관리 기능, P2는 후속 개발 또는 정책 협의가 필요한 기능입니다. 세부 기능의 우선순위는 기능 명세서를 따릅니다.

| 우선순위 | 주요 범위 |
| --- | --- |
| P0 | 로그인과 권한 검사, 담당 대상자 조회, 업무 요약, 우선순위와 근거, 주간 계획 확정, 현장 기록, 혜택 지원 상태, 내부 데모 연계 요청과 조회, 지역 선택과 기상특보, 주간 보고와 인쇄 |
| P1 | 담당자 배정 현황 조회, 구와 행정동 지표, 시설 검색과 지도, 권한 있는 처리자의 연계 결과 등록 |
| P2 | 계정 및 배정 관리, 대상자 원장 관리, AI 기록 요약, 최적 방문 동선, 안부ON 확장, 실제 업무시간 효과 측정 |

MVP는 가상 배정 명단을 사용합니다. 회원가입과 비밀번호 찾기는 현재 MVP 범위에 포함하지 않습니다. 기관 연계는 내부 데모 요청이며 실제 외부 기관으로 발송하는 기능을 전제로 하지 않습니다.

## 우선순위 점수

개인의 상대적 확인 우선순위를 다음 여섯 항목으로 설명합니다.

| 항목 | 초기 가중치 |
| --- | --- |
| 소득 취약 | 0.25 |
| 연령과 독거 | 0.20 |
| 건강과 낙상 이력 | 0.20 |
| 동네 환경 위험 | 0.15 |
| 계절 특보 | 0.10 |
| 확인 경과 | 0.10 |

점수는 위기 발생 확률이나 자동 선정 결과가 아닙니다. 각 항목의 입력값, 기여도, 근거, 출처, 기준일과 산식 버전을 함께 제공합니다. 정규화 방법, 등급 경계와 권장 확인 주기는 분석 담당자와 확정합니다.

누락된 값을 위험 없음이나 0점으로 바꾸지 않습니다. 여섯 항목이 완성되지 않은 점수는 `null`로 두고 별도 확인 필요 대상으로 구분합니다.

## 주요 업무 규칙

- 권한: 기관, 지역, 담당자 배정 범위에 따라 서버에서 조회와 변경 권한을 검사합니다. 관리자에게 모든 개인 상세 열람 권한을 자동으로 부여하지 않습니다.
- 계획과 실행: 추천/확정/보류 상태와 미진행/확인 완료/연락 실패 상태를 분리합니다. 확정에는 예정일시가 필요하며 보류와 추천 방식 변경에는 사유를 남깁니다.
- 성공 확인과 시도: 방문이나 전화가 성공한 경우 최근 성공 확인일을 갱신합니다. 실패 또는 거부한 경우 시도일만 갱신하며 재시도는 별도 기록으로 남깁니다.
- 혜택: 후보 안내는 최종 자격 판정이 아닙니다. 신청 완료와 기관 확인 수급을 분리하고 수급 확인에는 근거와 확인일을 남깁니다.
- 통계: 담당자의 배정 명단 집계와 주민 전체 통계를 구분합니다. 신청 완료만으로 지역의 실제 수급 통계를 변경하지 않습니다.
- 주간 확인율: 주간 시작 시점 점수 상위 20% 대상자를 분모로 고정하고, 주간 성공 확인한 고유 대상자를 분자로 사용합니다. 상위 20%와 HIGH 등급은 별개입니다.
- 연계 지표: 접수 소요시간은 요청부터 접수까지입니다. 완료율은 해당 주간 요청 중 조회시점까지 완료된 비율로 제안되어 있으며, 분모와 기준시각을 함께 제공합니다.
- 자료 없음과 장애: 0, 미수집, 미확인, 권한 제한을 구분합니다. 기상특보 수집 실패를 특보 없음으로 처리하지 않습니다.
- 저장과 이력: 중복 저장을 방지하고 동시 수정을 감지합니다. 변경자, 시각, 사유를 남기며 저장 결과가 상세, 큐, 점수, 혜택과 보고에 일관되게 반영되어야 합니다.
- 시간과 성과: 화면과 주간 업무는 한국시간 기준입니다. 이동시간과 문서 작성시간의 감소는 실제 측정 자료가 없으면 미측정으로 표시합니다.

## 데이터 사용

공개 실제 통계와 가상 개인 데이터를 명확히 구분합니다.

- 공개 자료: 지역 인구와 가구 통계, 시설 정보, 기상특보, 검토한 복지정책 안내 등을 사용합니다. 확보 상태와 기준일은 데이터 목록을 따릅니다.
- 가상 자료: 담당자, 대상자, 건강 상태, 수급 정보, 과거 연락 및 지원 이력과 데모 기관 정보를 생성합니다. 가상 여부와 생성 기준을 표시합니다.
- 기관 내부 자료: 실제 대상자 명단, 건강 기록, 수급 확인 정보 등은 운영 기관과의 별도 협의가 필요한 자료입니다.

외부 API 인증키와 자료 수집, 정제, 코드 대응은 백엔드에서 관리합니다. 자료별 출처, 기준일, 갱신 상태를 제공하며 공개 CSV를 프론트에서 매번 직접 처리하거나 외부 API 키를 노출하지 않습니다. 미확보 지표와 좌표는 임의로 생성하지 않으며, 명세에 정의한 가상 데이터 또는 자료 없음 표시를 사용합니다.

## 백엔드 작업 범위

백엔드는 FastAPI로 개발하며 프론트엔드는 별도 담당자가 구현합니다. API 요청서는 기능과 업무 규칙을 정의한 문서이므로 URL, HTTP 메서드, 요청과 응답 스키마, 오류 형식은 상세 설계가 필요합니다. 기능 명세의 `/clients` 같은 경로는 화면 경로이며 확정된 API 주소로 간주하지 않습니다.

| 요청 ID | 기능 |
| --- | --- |
| R01 | 로그인 및 계정 이용 |
| R02 | 사용자 및 관리 기능 |
| R03 | 대상자 조회 및 사례관리 |
| R04 | 담당자 대시보드 |
| R05 | 방문 및 전화 계획 |
| R06 | 위험점수 및 추천 근거 |
| R07 | 현장 기록 및 체크리스트 |
| R08 | 복지혜택 안내 및 신청지원 |
| R09 | 부서 연계 및 처리 관리 |
| R10 | 지역 현황 및 자원 정보 |
| R11 | 주간 보고 및 성과 집계 |

backend와 db-server는 독립된 GitHub 레포로 개발합니다. backend는 API 코드·DB 접속·조회/저장을 담당하고, db-server는 PostgreSQL 실행·테이블 생성/변경·초기 데이터를 관리합니다. 데이터 형식은 dto에 정의하고, API별 업무 로직과 SQL 조회·저장은 service에서 함께 처리합니다.

배포 방향은 Raspberry Pi 5 8GB와 NVMe SSD의 Ubuntu Server에서 각 레포의 Docker 설정으로 API와 PostgreSQL을 실행하는 구성입니다. backend는 DATABASE_URL로 DB에 접속합니다. 개발 접근은 Tailscale, 공개 데모는 Tailscale Funnel을 사용하는 방향이며 실행·배포 설정은 아직 작성하지 않았습니다.

## 상세 설계에서 확정할 사항

- 점수 정규화, 등급 경계, 권장 확인 주기와 동률 순서
- 혜택 확인 필요 여부가 추천 큐의 순서에 영향을 주는지와 반영 규칙
- 미확인 인원의 정의와 배정 변경의 집계 반영 시점
- 상위 20% 인원 반올림, 동률, 결측과 배정 변경 처리
- 체크리스트 최종 문항과 입력 기준
- 혜택 규칙의 공식 근거 및 검토일, 데이터 미확보 시 사용할 대체안
- API 계약, 인증 방식, 중복 저장 방지와 동시 수정 처리 방식

PDF에 등장하는 ARS 자동 전화, 담당자 가용 시간에 따른 방문 주기 자동 재배분, 위기 예측모델은 현재 세 DOCX의 구현 요구사항으로 확정되어 있지 않습니다. AI 요약과 최적 방문 경로는 명세에 따라 P2로 둡니다.
