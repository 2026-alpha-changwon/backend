# backend 레포 구조 설계

backend는 역할별 계층형 구조의 FastAPI API 서버입니다. handler가 HTTP 요청을 받고 service가 업무 처리와 DB 조회·저장을 함께 담당합니다. main.py는 backend 레포 루트에 둡니다.

이 문서는 현재 구현 상태와 앞으로의 배치 기준을 정리합니다. 필요한 기능부터 파일을 추가하고 실제 구조가 바뀌면 문서도 함께 갱신합니다. 아래 처리 흐름과 기능별 파일은 구현 예정입니다.

## 레포별 책임

backend와 db-server는 독립된 GitHub 레포입니다. 현재 로컬 폴더 이름은 backend와 db입니다. 각각의 Docker 실행 설정과 환경변수를 관리합니다.

| 레포 | 담당 |
| --- | --- |
| backend | API·인증·업무 로직·DB 접속·조회/저장·외부 API 연동·API 실행 설정 |
| db-server | PostgreSQL 실행 설정·볼륨·테이블 생성 SQL·변경 이력·초기 데이터·DB 백업 |

backend는 DATABASE_URL로 PostgreSQL에 접속합니다. DB 구조는 db-server의 SQL로 관리합니다. backend의 데이터 형식은 dto에 정의하고 service가 SQL을 실행해 조회 결과를 DTO로 변환합니다. DB 스키마가 바뀌면 관련 SQL과 DTO를 함께 확인합니다.

기존 12개 테이블 설계와 개발 단계의 동시 로그인 허용을 유지합니다.

로그인 구현은 뒤로 미루고, 초기 개발 대상으로 대상자 목록·상세 조회를 검토하고 있습니다. 이후 기능의 구현 순서는 진행 상황에 맞춰 정합니다. 파일이 많아져 불편해지면 dto·handler·service 폴더를 해체하고 큰 기능별 폴더에 관련 파일을 함께 모읍니다. 체크리스트와 점수 설정의 미확정 정책은 확정 후 반영합니다.

## 폴더별 책임

| 폴더 | 책임 | 주요 사용 관계 |
| --- | --- | --- |
| handler | URL·HTTP 메서드, DTO 입력, 인증 확인, service 호출, 응답·쿠키 처리 | dto, service, util |
| dto | 요청·응답 형식, 필수값·자료형 검증 | Pydantic과 기본 자료형 |
| service | 업무 조건·권한 검사, SQL 조회·집계·저장, 결과 DTO 변환, 트랜잭션 | dto, data, config, 공통 util |
| data | 외부 API 호출, CSV 등 원천 자료 읽기, 형식 정제, 수집 메타데이터 반환 | config, util/cache.py |
| config | 설정값·DB 연결 구성·규칙 파일 | 환경변수·DB 드라이버 |
| util | 공통 응답·해시·토큰·인증 연결·시간·파일 캐시 | 기능에 필요한 하위 공통 코드 |

service가 DB 연결로 쿼리를 실행하고 커밋·롤백을 결정합니다. SQL과 입력 매개변수를 분리해 실행하고 조회한 행을 응답 DTO로 변환합니다. 외부 연동은 자료와 출처·기준일·수집 상태를 반환하며 업무에서의 적용 여부는 service가 판단합니다. 응답 DTO에는 비밀번호 해시·세션 원문 등 내부 저장값을 포함하지 않습니다.

service는 기능별 함수 단위로 작성합니다. 반복되는 조회는 service 안의 함수로 분리해 재사용하고, 하나의 업무에 필요한 여러 쿼리는 같은 DB 연결에서 처리합니다.

## API별 파일과 DB 접근

| 요청 | handler·dto·service의 기능명 | 담당 업무 | 조회·저장 대상 |
| --- | --- | --- | --- |
| R01 | auth | 로그인·로그아웃·현재 로그인 사용자 | users |
| R02 | user | 사용자·기관·담당 범위·배정 현황 | users, organizations, regions, client_assignments |
| R03 | client | 대상자 목록·상세·통합 이력 | clients와 배정·연락·혜택·연계 기록 |
| R04 | dashboard | 담당자 업무 요약 | 배정·점수·계획·혜택 집계 |
| R05 | plan | 방문·전화 계획 | care_plans, client_assignments, risk_snapshots |
| R06 | risk | 점수 산출·근거·계산 상태 | risk_snapshots, clients |
| R07 | contact | 체크리스트·현장 기록 | contact_records, clients, care_plans, client_benefits |
| R08 | benefit | 혜택 후보·신청지원 | benefits, client_benefits, clients |
| R09 | referral | 기관 연계 | referrals, organizations, contact_records |
| R10 | region | 지역·시설·기상 | regions와 data의 외부 자료 |
| R11 | report | 주간 기준 집합·활동 집계 | weekly_snapshots와 연락·혜택·연계 집계 |

예를 들어 client 기능은 handler/client_handler.py, dto/client_dto.py, service/client_service.py로 구성합니다. client_service.py 안에서 대상자 조회·검색·필터·정렬 쿼리와 업무 권한 검사를 처리합니다.

로그인 구현 시 현재 사용자 정보는 GET /auth/me에서 제공할 예정이며, user 기능은 담당 범위·기관·담당자·배정 현황을 담당합니다.

## 요청 처리 흐름

```text
프론트 요청
  → handler: DTO로 입력 수신·현재 사용자 확인
  → service: 업무 권한·조건 검사·SQL 조회·저장
  → service: 변경 묶음을 커밋하거나 롤백
  → handler: 응답 DTO·공통 응답·쿠키 처리
```

오류는 service에서 util/errors.py의 업무 예외로 전달하고, main.py에 등록한 util/response.py의 오류 처리 함수가 HTTP 응답으로 바꿉니다. 입력 검증 오류도 같은 응답 규칙을 사용합니다.

## 로그인과 세션 설계

로그인은 후속으로 구현하며 다음 흐름을 기준으로 합니다.

1. auth_handler가 로그인 DTO를 받고 auth_service를 호출합니다.
2. auth_service가 DB에서 계정을 조회하고 util/password.py로 비밀번호를 검증합니다.
3. auth_service가 util/session.py로 토큰과 만료시각을 만들고 users.sessions에 해시·만료시각을 저장합니다. 사용자 행 잠금과 커밋은 동일 트랜잭션에서 수행합니다.
4. auth_service가 사용자 정보 DTO와 세션 값을 전달하면 auth_handler가 응답을 반환하고 HttpOnly 쿠키를 설정합니다.
5. 다음 요청에서는 util/authentication.py가 쿠키를 읽어 auth_service의 세션 조회 함수를 호출합니다. 로그인된 사용자를 handler에 제공합니다.

auth_service는 util/password.py와 util/session.py를 사용합니다. 요청 인증 연결 함수인 util/authentication.py는 handler에서 사용합니다. 이렇게 모듈의 호출 방향을 구분합니다.

동시 로그인은 허용하며 로그아웃은 해당 세션만 폐기합니다. 세션 만료·계정 비활성 여부는 인증 시 확인합니다. 기관·지역·담당 배정에 따른 업무 접근 범위는 각 service에서 검사합니다.

## 현장 기록 저장

contact_handler는 입력을 받고 contact_service를 호출합니다. contact_service는 대상자·계획·체크리스트를 검증하고 하나의 DB 연결에서 연락 저장, 현재 정보 반영, 계획 상태 변경, 함께 입력한 혜택 행동을 처리합니다. 전체 쿼리를 한 트랜잭션으로 실행하고 커밋합니다. 실패하면 전체를 롤백합니다.

점수 재산출은 기록 저장 후 risk_service에서 수행합니다. 점수 실패 상태와 연락 기록 저장 결과는 구분합니다. 계산 입력 버전·과거 근거 보존은 DB 설계를 따릅니다.

## 설정과 실행

- main.py는 handler·공통 오류 처리·CORS·서버 수명주기를 연결합니다.
- 환경별 DB 주소·쿠키 설정·외부 API 키는 환경변수로 읽습니다. 예시는 .env.example에 두고 실제 비밀값은 버전 관리에서 제외합니다.
- .dockerignore는 실제 환경변수 파일·캐시·개발용 파일을 API 이미지의 빌드 컨텍스트에서 제외합니다.
- 공개 자료 캐시 경로는 설정으로 지정하고 Docker 영속 볼륨에 연결합니다. 수집 상태와 마지막 성공 자료를 구분합니다.
- backend의 Dockerfile·compose.yaml은 API 컨테이너를 실행합니다. PostgreSQL과 DB 볼륨은 db-server의 실행 설정에서 관리합니다.
- 동일한 Raspberry Pi에 배포할 때는 두 레포의 Compose를 공유 Docker 네트워크에 연결합니다. DB 호스트명과 접속 정보는 DATABASE_URL로 전달합니다.
- 라즈베리파이는 Ubuntu Server 64비트 ARM64 환경을 기준으로 합니다. 맥과 공통 코드·Docker 설정을 사용하고 환경별 .env와 데이터 볼륨을 관리합니다. OS별 브랜치는 나누지 않습니다.
- db-server에서 테스트용 데이터를 준비하면 backend에서 DB 연결과 구현한 API를 검증합니다. API 테스트는 TEST_DATABASE_URL로 분리한 테스트 DB를 사용합니다.

DB 설계와 테이블 정의는 DB 레포의 docs/01_DB_설계.md와 docs/02_테이블_정의.md에서 관리합니다. 실제 생성·변경 SQL은 db-server 레포에서 개발합니다. 현재 backend에는 빈 역할별 폴더와 루트 파일이 준비되어 있습니다. main.py·Dockerfile·compose.yaml은 빈 파일이며 실행 코드는 이후에 구현합니다.

## 처음 구현할 범위

로그인 구현을 뒤로 미루기로 했으며, 다음 순서로 대상자 조회부터 시작하는 방안을 검토합니다.

1. db에서 지역·기관·가상 대상자 초기 데이터를 준비합니다.
2. config/settings.py와 config/database.py로 설정·DB 접속을 구성합니다.
3. 대상자 목록·상세 조회의 API 경로와 요청·응답 형식을 정하고 Swagger에 반영합니다.
4. 필요한 client DTO·handler·service를 구현하고 DB 조회와 응답을 연결합니다.
5. 조회 결과를 확인하고 프론트와 연동합니다. 로그인·세션은 후속으로 연결합니다.

개발 중 사용자 식별이 필요한 부분은 임시 고정 사용자로 처리하는 방안을 제안한 상태입니다. 조회 API의 상세 계약과 개발용 인증 처리 방식은 아직 확정하지 않았습니다.

## 초기 파일 준비 상태

config·dto·handler·service·util·data·tests는 내부 파일 없이 생성했습니다. 위 전체 파일 목록은 이후 기능을 구현할 때의 배치 기준입니다. requirements.txt에는 기본 서버 패키지를 적었으며 패키지 설치는 진행하지 않았습니다.

Git은 빈 폴더를 보관하지 않으므로 원격 레포를 내려받으면 빈 역할별 폴더는 나타나지 않습니다. 해당 기능의 파일을 추가할 때 폴더도 함께 반영됩니다.

[swagger.yaml](../swagger.yaml)에 먼저 정한 인증 API 세 개를 OpenAPI 3.0.3 형식으로 작성했습니다. 서버 실행 전 API 계약을 확인하는 초안입니다.
