# backend 레포 구조 설계

backend는 역할별 계층형 구조의 FastAPI API 서버입니다. handler가 HTTP 요청을 받고 service가 업무 처리와 DB 조회·저장을 함께 담당합니다. main.py는 backend 레포 루트에 둡니다.

이 문서는 현재 구현 상태와 앞으로의 배치 기준을 정리합니다. R03 대상자 조회, R05 방문 및 전화 계획, R07 현장 기록을 구현했습니다. 아래 파일 배치에는 앞으로 추가할 기능도 포함합니다.

## 레포별 책임

backend와 db는 독립된 레포이며 로컬에서도 형제 폴더로 관리합니다. 기존 문서의 db-server는 db 레포를 가리킵니다. 각 레포에서 Docker Compose와 환경변수를 관리하고 라즈베리파이에서 API와 PostgreSQL을 각각의 컨테이너로 실행합니다.

| 레포 | 담당 |
| --- | --- |
| backend | API·인증·업무 로직·DB 접속·조회/저장·외부 API 연동·API 실행 설정 |
| db | PostgreSQL 실행 설정·볼륨·테이블 생성 SQL·변경 이력·초기 데이터·DB 백업 |

backend는 DATABASE_URL로 PostgreSQL에 접속합니다. DB 구조는 db의 SQL로 관리합니다. backend의 데이터 형식은 dto에 정의하고 service가 SQL을 실행해 조회 결과를 DTO로 변환합니다. DB 스키마가 바뀌면 관련 SQL과 DTO를 함께 확인합니다.

2026-11-15 기준, DB는 backend 명세에 맞춘 32개 테이블 설계를 따릅니다. 테이블·컬럼 수 제한은 해제됐습니다. DB 담당이 사용자 실행 출력으로 라즈베리파이 PostgreSQL 17.11, 테이블 32개, 대상자 12명, 연락 기록 4개와 next_check_date의 NOT NULL 및 NULL 행 0건을 확인했습니다. DB 컨테이너 healthy와 네트워크 연결도 확인됐습니다. backend는 기존 SQL·seed를 넣은 임시 PostgreSQL에서 R03 조회를 검증했으며 API 컨테이너의 실제 연결은 backend 배포 시 확인합니다. 개발 단계의 동시 로그인 허용은 유지합니다.

개인 자료는 모두 가상이며 실제 대상자에게 서비스하지 않습니다. clients에 is_demo 컬럼을 두지 않고 R03 응답의 data_mode=`DEMO`로 가상 자료임을 표시합니다.

## 폴더별 책임

| 폴더 | 책임 | 주요 사용 관계 |
| --- | --- | --- |
| handler | URL·HTTP 메서드, DTO 입력, 인증 확인, service 호출, 응답·쿠키 처리 | dto, service, util |
| dto | 요청·응답 형식, 필수값·자료형 검증 | Pydantic과 기본 자료형 |
| service | 업무 조건·권한 검사, SQL 조회·집계·저장, 결과 DTO 변환, 트랜잭션 | dto, data, config, 공통 util |
| data | 외부 API 호출, CSV 등 원천 자료 읽기, 형식 정제, 수집 메타데이터 반환 | config, util/cache.py |
| config | 환경 설정값·DB 연결 구성 | 환경변수·DB 드라이버 |
| util | 공통 응답·해시·토큰·인증 연결·시간·파일 캐시 | 기능에 필요한 하위 공통 코드 |

service가 DB 연결로 쿼리를 실행하고 커밋·롤백을 결정합니다. SQL과 입력 매개변수를 분리해 실행하고 조회한 행을 응답 DTO로 변환합니다. 외부 연동은 자료와 출처·기준일·수집 상태를 반환하며 업무에서의 적용 여부는 service가 판단합니다. 응답 DTO에는 비밀번호 해시·세션 원문 등 내부 저장값을 포함하지 않습니다.

service는 기능별 함수 단위로 작성합니다. 반복되는 조회는 service 안의 함수로 분리해 재사용하고, 하나의 업무에 필요한 여러 쿼리는 같은 DB 연결에서 처리합니다.

표는 주요 접근 대상을 요약합니다. 변경 요청의 중복 방지는 mutation_requests를 업무 저장과 같은 트랜잭션으로 처리합니다. 전체 관계와 컬럼은 db/docs/02_테이블_정의.md를 따릅니다.

예를 들어 client 기능은 handler/client_handler.py, dto/client_dto.py, service/client_service.py로 구성합니다. client_service.py 안에서 대상자 조회·검색·필터·정렬 쿼리와 업무 권한 검사를 처리합니다.

로그인 구현 시 현재 사용자 정보는 GET /auth/me에서 제공할 예정이며, user 기능은 담당 범위·기관·담당자·배정 현황을 담당합니다.

## 요청 처리 흐름

```text
프론트 요청
  → handler: DTO로 입력 수신·현재 사용자 확인
  → service: 업무 권한·조건 검사·SQL 조회·저장
  → service: 변경 묶음을 커밋하거나 롤백
  → handler: 응답 DTO·공통 응답·쿠키 처리
```

service의 util/errors.py 업무 예외와 입력 검증 오류를 main.py에 등록한 공통 오류 처리기로 전달합니다. util/response.py의 성공·페이지·오류 응답 생성 함수를 사용하며, 실패 응답은 data=null과 error의 code·message·details 형식입니다.

## 로그인과 세션 설계

로그인은 후속으로 구현하며 다음 흐름을 기준으로 합니다.

로그인 구현 전에는 `.env`의 `DEV_USER_ID`와 `CONTACT_WRITE_DEV_USER_ID`에 같은 공통 개발 담당자 UUID를 설정합니다. `util/authentication.py`는 조회와 저장에 해당 계정을 제공하므로 프론트는 쿠키 없이 업무 API를 호출합니다. 담당자의 기관, 지역, 현재 배정으로 접근 범위를 계산합니다.

`DEV_USER_ID`가 비어 있으면 util/authentication.py가 쿠키를 읽고 auth_service.get_session_user_id가 SHA-256 해시로 user_sessions와 활성 계정을 확인합니다. 만료·폐기된 세션과 비활성 계정은 401입니다. 로그인 발급·내 정보·로그아웃 API는 후속으로 구현합니다. 테스트에서는 get_current_user_id를 주입하여 여러 담당자의 권한을 확인합니다.

1. auth_handler가 로그인 DTO를 받고 auth_service를 호출합니다.
2. auth_service가 DB에서 계정을 조회하고 util/password.py로 비밀번호를 검증합니다.
3. auth_service가 util/session.py로 토큰과 만료시각을 만들고 user_sessions에 user_id·token_hash·expires_at을 저장합니다. 원문 토큰은 DB에 저장하지 않습니다.
4. auth_service가 사용자 정보 DTO와 세션 값을 전달하면 auth_handler가 응답을 반환하고 HttpOnly 쿠키를 설정합니다.
5. 다음 요청에서는 util/authentication.py가 쿠키를 읽어 auth_service의 세션 조회 함수를 호출합니다. 로그인된 사용자를 handler에 제공합니다.

auth_service는 util/password.py와 util/session.py를 사용합니다. 요청 인증 연결 함수인 util/authentication.py는 handler에서 사용합니다. 이렇게 모듈의 호출 방향을 구분합니다.

동시 로그인은 허용하며 로그아웃은 해당 user_sessions 행의 revoked_at을 기록해 현재 세션만 폐기합니다. 세션 만료·계정 비활성 여부는 인증 시 확인합니다. 기관·지역·담당 배정에 따른 업무 접근 범위는 각 service에서 검사합니다.

## 현장 기록 저장

`contact_service.py`는 대상자와 체크리스트 조회를 처리합니다. `contact_write_service.py`는 한 트랜잭션에서 현장 기록과 답변을 저장하고, 연결한 계획의 실행 상태가 달라지면 새 계획 버전과 이벤트를 기록합니다. 실패하면 전체를 롤백합니다. 계획을 연결할 때 현재 버전으로 변경 충돌을 확인하고 실제 연락 시각의 버전을 이력에 남깁니다.

R05의 `plan_query_service.py`는 기존 추천 배치와 오늘 확정 방문을 조회합니다. `plan_update_service.py`는 계획 검토 상태, 일정, 연락 방식을 변경하고 전후 상태를 저장합니다. 두 기능의 쓰기는 대상자 행을 먼저 잠가 현장 기록과 계획 변경이 같은 순서로 처리되도록 합니다.

점수 재산출은 기록 저장 후 risk_service에서 수행합니다. 점수 실패 상태와 연락 기록 저장 결과는 구분합니다. clients의 input_version·계산 run과 risk_snapshots·risk_factors를 연결하고 과거 실행이 최신 계산 상태를 덮어쓰지 않도록 DB 설계를 따릅니다.

체크리스트와 점수 산식의 원본은 DB의 불변 버전 테이블(checklist_versions·checklist_questions, risk_models·risk_model_factors)입니다. 설정 파일을 사용한다면 초기 seed나 배포 입력으로만 사용하고, 연락·점수 기록은 실제 사용한 DB 버전을 참조합니다.

## 설정과 실행

- main.py는 handler·공통 오류 처리·CORS·서버 수명주기를 연결합니다.
- 환경별 DB 주소·쿠키 설정·외부 API 키는 환경변수로 읽습니다. 예시는 .env.example에 두고 실제 비밀값은 버전 관리에서 제외합니다.
- .dockerignore는 실제 환경변수 파일·캐시·개발용 파일을 API 이미지의 빌드 컨텍스트에서 제외합니다.
- 공개 자료 캐시 경로는 설정으로 지정하고 Docker 영속 볼륨에 연결합니다. 수집 상태와 마지막 성공 자료를 구분합니다.
- backend의 Dockerfile·compose.yaml은 API 컨테이너를 실행합니다. PostgreSQL과 DB 볼륨은 db의 실행 설정에서 관리합니다.
- 동일한 Raspberry Pi에서 두 레포의 Compose를 DB 네트워크 meonjeogayo-db_default에 연결합니다. backend는 external 네트워크로 참여하며 DATABASE_URL은 DB 서비스의 postgres:5432를 사용합니다. 이 접속 구성은 DB 담당이 실제 Compose 정규화 결과로 확인했습니다.
- 라즈베리파이는 Ubuntu Server 64비트 ARM64 환경을 기준으로 합니다. 맥과 공통 코드·Docker 설정을 사용하고 환경별 .env와 데이터 볼륨을 관리합니다. OS별 브랜치는 나누지 않습니다.
- Mac 저장공간을 아끼며 기존 Python 패키지를 활용하는 .venv에 PostgreSQL 드라이버를 추가했습니다. SQL 실행 검증은 임시 폴더의 PostgreSQL 18.6과 복제한 스키마·합성 seed로 진행했고 검증 서버와 데이터는 종료·정리했습니다.
- 실제 API 서버는 Raspberry Pi의 backend 컨테이너에서 실행합니다. Mac에서 코드를 개발·검증한 뒤 커밋·원격 푸시하고, Raspberry Pi에서 원격 코드를 받아 docker compose up -d --build로 빌드·실행합니다.
- DB 실행 상태·스키마·초기 데이터·DB 컨테이너 관련 작업은 DB 담당 채팅에 인계합니다. backend 담당은 DB가 확인한 접속 구성에 맞춰 API 컨테이너를 연결합니다.
- R05의 실제 DB 검증은 기존 `changwon_dev`의 한 트랜잭션에서 가상 데이터를 사용합니다. 종료 시 롤백하고 읽기 전용 연결에서 검증용 레코드가 남지 않았는지 확인합니다.

DB 설계와 테이블 정의는 DB 레포의 docs/01_DB_설계.md와 docs/02_테이블_정의.md에서 관리합니다. 실제 생성·변경 SQL은 db 레포에서 개발합니다. main.py에 서버·R03 handler·CORS·공통 오류 처리를 연결했습니다. Dockerfile은 Python 3.13 기반 API 이미지를 만들고, compose.yaml은 API 컨테이너·포트·환경변수·DB 네트워크·재시작·HTTP healthcheck를 구성합니다. Compose 정적 검증을 완료했으며 실제 이미지 빌드·라즈베리 실행은 배포 시 확인합니다.

## 처음 구현할 범위

R03 전체(CLI01~CLI05)를 첫 개발 범위로 유지합니다. 등록·삭제·기본정보 수정 CLI06은 기존 P2입니다.

1. db/init/01_schema.sql과 db/docs/02_테이블_정의.md·03_명세_대응.md를 기준으로 R03의 API 경로·요청·응답 DTO 및 Swagger 계약을 작성했습니다.
2. config/settings.py·config/database.py 및 client DTO·handler·service를 작성했습니다. 권한·검색·필터·정렬·페이지·상세·통합 이력을 전체 범위로 구현했습니다. 요청별 READ ONLY·REPEATABLE READ 트랜잭션에서 같은 연결과 조회 기준시각을 사용합니다.
3. 임시 PostgreSQL에 준비된 스키마·seed를 적용하여 19개 API 테스트를 통과했습니다. 실제 세션 쿠키·만료·폐기·계정 비활성, 미확인/누락 프로필, 현재/이전 위험결과, 큰 페이지 및 읽기 전용 트랜잭션도 추가 검증했습니다. 라즈베리 DB 상태는 DB 담당이 확인을 마쳤고, backend의 라즈베리 컨테이너 실행과 프론트 연동은 배포 단계에서 확인합니다.

R03 HTTP 계약은 swagger.yaml과 dto/client_dto.py에 작성했습니다. GET /clients, GET /clients/{client_id}, GET /clients/{client_id}/history의 세 경로를 사용합니다. 공통 응답은 dto/common_dto.py의 data·error 형식과 util/response.py를 사용합니다. 현재 사용자는 get_current_user_id에서 받고, 기관·사용자 지역의 교집합과 현재 유효한 담당 배정을 검사합니다. 구 단위 허용 범위는 유효한 하위 동에 적용합니다. 현재 사용자의 ID를 요청 쿼리로 받지 않습니다.

R03 조회 시 대상자 한 행을 유지하고, 최신 프로필 revision·점수 run/input 세대·성공 확인과 연락 시도·통합 이력 규칙을 인계 문서에 맞춥니다. 2026년 11월 10일 확정한 혜택 확인 필요 기준은 해당 대상자의 client_benefits 중 support_status가 NEEDS_REVIEW인 행이 하나 이상 있는지입니다. EXISTS 조회로 대상자별 boolean을 만들고 목록·상세·필터에 같은 조건을 적용합니다. 나머지 업무 정책의 확정 상태는 db/docs/03_명세_대응.md의 U01~U10과 최신 공유 기록을 확인합니다. 정책 미설정 상태를 명시하고 임의 값을 확정하지 않습니다.

DB 전체 설계는 32개이며 최신 생성 SQL과 개발 데이터는 db 레포에서 관리합니다. DB 측 적용 상태와 backend의 실제 연결·조회 검증 상태를 각각 확인합니다.

## 현재 구현 상태

라즈베리파이에 R03 조회와 R07 체크리스트 및 현장 기록 저장이 배포되어 있습니다. R05 주간 큐 조회, 오늘 확정 방문 조회, 계획 검토 변경과 R07 계획 연결은 작업 트리에 구현했습니다. 통합 경로는 `tests/test_plans.py`에서 검증합니다.

Git은 빈 폴더를 보관하지 않으므로 원격 레포를 내려받으면 빈 역할별 폴더는 나타나지 않습니다. 해당 기능의 파일을 추가할 때 폴더도 함께 반영됩니다.

[swagger.yaml](../swagger.yaml)은 R03, R05, R07의 계약과 인증 API 초안을 OpenAPI 3.1.0 형식으로 제공합니다. 각 서버의 `/docs`와 `/openapi.json`에는 실행 중인 버전에 등록된 API가 표시됩니다.
